# 酷澎訂單管理系統（Coupang OMS）

永豐商店 OP 團隊的中繼站。把酷澎整合表無腦整份上傳，系統自動去重、
抓出酷澎偷偷改過的單、記錄誰在什麼時候改了什麼，最後一鍵匯出乾淨的 Excel。
另外還有一個跟訂單管理完全獨立的「採購表轉換」工具（見下方「採購表轉換」段落）。

## 正式站：部署在 Render

**日常使用的正式站跑在 [Render](https://render.com)，資料存在 Supabase 的
PostgreSQL 資料庫**，不是本機程式、也不需要誰的電腦開著。同事直接打開
正式站網址就能用，跟誰的電腦有沒有開機無關。

判斷資料庫走哪一種，看有沒有設 `DATABASE_URL` 這個環境變數（見 `db.py`
開頭的說明）：

| | 本機開發 | Render 正式站 |
|---|---|---|
| 資料庫 | SQLite（存在本機檔案） | PostgreSQL（Supabase，雲端） |
| `DATABASE_URL` | 不設 | 設成 Supabase 的連線字串 |
| 資料存活期 | 跟著這台電腦的檔案 | 跟部署無關，重新部署資料不會消失 |
| 帳號密碼、下拉選單設定 | `資料與設定/` 底下的 JSON 檔 | 資料庫的 `app_settings` 表 |

**怎麼發佈更新**：改完程式碼、`git push` 到 Render 有接的那個分支，Render
會自動抓最新程式碼重新部署，通常一兩分鐘內會生效。**不需要**手動下載、
解壓縮、覆蓋任何資料夾——那是本機開發模式才有的流程（見下面「本機開發
與測試」）。

發佈完怎麼確認真的生效了：打開正式站頁面，看畫面右下角的版本號
（`BUILD_VERSION`，定義在 `app.py` 最上面），跟程式碼裡改完之後手動升過
的版號比對；不一致就代表 Render 那次部署還沒跑完或失敗，去 Render 後台
看部署紀錄。**每次改完程式碼記得手動升這個版號**，不然沒辦法用這個方式
確認部署有沒有生效。

正式站怎麼接哪個 GitHub 分支、環境變數怎麼設，在 Render 後台的
服務設定頁看得到最準確的現況——這份文件只記錄「系統本身知道怎麼判斷
自己在哪種模式下跑」，不是 Render 專案設定的存檔，實際設定隨時可能在
Render 後台被調整，遇到跟這裡寫的對不上時以 Render 後台顯示的為準。

## 本機開發與測試

改程式碼時想在自己電腦上先跑一次確認沒壞掉，或想在沒有網路、不想動到
正式資料的情況下測試，可以本機跑（這時候會自動用 SQLite，不會去動
Supabase 上的正式資料）：

```bash
pip install -r requirements.txt   # 第一次要先裝一次
python app.py                     # 或 Windows 上雙擊 START.bat
```

開 <http://127.0.0.1:5000>。本機模式下資料庫檔案跟設定檔存在程式資料夾
「外面」的 `資料與設定/` 資料夾（`db.py` 的 `DATA_DIR`），程式碼跟資料
分開，方便日後升級或搬移。

驗證系統邏輯是否正常（用真實資料跑完整流程）：

```bash
python test_flow.py      # 訂單管理主流程，184 項檢查
python test_purchase.py  # 採購表轉換（跟訂單管理完全獨立），48 項檢查
```

## 核心防呆（這幾條是系統的命）

| 防呆 | 做法 |
|---|---|
| **一張 PO 有多個 SKU** | 唯一鍵是 `UNIQUE(po_number, sku_id)`。**不能**把 `po_number` 設成 UNIQUE——真實整合表裡一張 PO 最多有 29 個 SKU，那樣做會靜悄悄丟掉 80% 的資料、害倉庫少出貨。 |
| **改倉／改期不能變成新單** | `warehouse` 和 `delivery_date` 是整張 PO 共用、而且天天在改的欄位，所以它們是一般欄位、不進主鍵。放進主鍵會讓酷澎改倉時判定成「新單」而 INSERT 一份，產生數量翻倍的幽靈列。 |
| **重複 ≠ 變更** | 內容完全相同才靜默略過；只要數量／交期／倉別有差，就是酷澎偷改單，一律更新 + 寫歷程 + 標記待確認推到最上面。 |
| **消失 ≠ 取消** | 酷澎後台一次只給 20–60 筆，上傳的永遠可能是片段。資料庫有、檔案沒有的單，系統**完全不動**，只更新 `last_seen_at`。任何取消判定都必須由人決定。 |
| **匯入不覆蓋 OP 心血** | `qty_coupang` 只有匯入能改，`qty_ship` 只有人能改。OP 一旦手動調整過出貨數量（`qty_ship_overridden`），之後匯入永遠不再碰它。 |
| **全有全無** | 匯入分兩階段：先預覽報告（新增／更新／略過各幾筆、酷澎改了什麼），OP 按確認才實際寫入，中途任何一列出錯整批 rollback。寫入前自動備份 `database.db` 到 `backups/`（僅本機 SQLite 模式；Postgres 模式的備份見下方「備份」）。 |
| **多人同時用不互蓋** | SQLite 開 WAL 模式、PostgreSQL 本來就是多人資料庫，解決資料庫層的鎖；業務層用 `version` 樂觀鎖，同事先存過就回 409 並提示重新載入，不會 last-write-wins。 |
| **歷程是證據** | `edit_logs` 是 append-only 的**欄位級**紀錄：哪張單／哪個欄位／改前／改後／誰／何時／來源（匯入 or 手動）。不存成一句中文字串，這樣才查得出「這個月被改過交期的單有哪些」。 |
| **匯出即拉單，但要 OP 自己決定** | 匯出時的「標記為已拉單」是可勾選的。試算匯出不會鎖單；正式匯出才標記 `is_pulled` 並鎖定編輯，取代以前每天複製一個 Excel 分頁記「拉到哪」的做法。 |
| **已拉單後又被改 = 最高警示** | 倉庫已經拿到舊資料了。這種單在匯入預覽階段就會先跳紅字警告，匯入後標成 `changed_after_pull`，在列表最頂端用紅底顯示。 |
| **解鎖要留原因** | 解除拉單鎖定必須填理由，理由會寫進歷程。 |
| **正規化只有一份實作** | `normalize.py` 是唯一入口。PO 單號強制當文字（否則 13 位數會被 Excel 轉成科學記號變成另一把鍵）、交期一律轉 ISO、倉別去空白轉大寫。匯入、查詢、比對全走同一條路徑。 |

## 拆單

酷澎拆單會產生**新的 PO 單號**，所以走的是一般的「新增」路徑，不需要任何猜測邏輯。
`parent_po` 欄位保留原訂單號做血緣追蹤，列表上會以 `↳原單 xxx` 顯示。

## 採購表轉換

跟酷澎訂單管理系統**完全獨立**的工具（`purchase.py`、`templates/purchase.html`），
不寫資料庫、不共用任何一張訂單表。畫面頂端有獨立的入口按鈕，網址是 `/purchase`。

依線別（P&G／紙潔／瑪氏）把酷澎「訂單匯入」Excel 轉成各線別自己要用的
「產品採購表」格式，三個線別各自沿用公司既有的 `.xls` 範本檔
（`purchase_templates/`，用 `xlutils` 只覆寫資料列，查表工作表跟儲存格
樣式原封不動保留）。細節看 `purchase.py` 開頭的說明。

## 匯出格式怎麼對齊 ERP

**本機 SQLite 模式**：打開「資料與設定」資料夾裡的 `export_profiles.json`，
找到 `erp` 這個 profile，把 `columns` 改成公司 ERP 匯入規範要求的欄位名稱
與順序即可，**不需要動任何程式碼**：

```json
{ "header": "ERP 欄位名稱", "field": "系統內部欄位", "format": "text|int|date|decimal" }
```

- `header` 想叫什麼就叫什麼，順序就是匯出欄位的順序
- `const` 可以輸出固定值（ERP 常見的公司別、單別等常數欄位）
- 改完存檔、重新整理網頁就生效

要新增其他格式（例如不同倉庫要不同版本），直接在 `profiles` 底下多加一個
區塊就會出現在匯出選單裡。

**Render／PostgreSQL 正式站**：這份設定改存在資料庫的 `app_settings` 表，
不是檔案，沒辦法直接編輯。只有資料庫裡**完全還沒有這筆設定**時（例如全新
的資料庫）才會拿 `defaults/export_profiles.json` 種一份進去——**已經種過
之後，改 `defaults/export_profiles.json` 再重新部署不會生效**，因為資料庫
裡已經有值了，不會被覆蓋。要調整正式站現有的匯出格式，目前得直接改資料庫
裡 `app_settings` 那一列的內容（或請人加一個線上編輯畫面），不能像本機
模式那樣直接改檔案生效。

## 備份

**本機 SQLite 模式**：每次匯入寫入前會自動把 `database.db` 複製到
「資料與設定/backups/」，保留最近 30 份。那只防「匯入出錯」，防不了整個
資料夾被誤刪，建議定期把「資料與設定」資料夾複製一份到公司雲端硬碟。

**Render／PostgreSQL 正式站**：資料庫本體交給 Supabase 管理，備份策略以
Supabase 後台的設定為準（多數方案內建每日自動備份，實際保留天數看方案
等級）。系統這邊沒有另外做應用層的備份邏輯，如果需要更嚴謹的備份頻率
或還原演練，要在 Supabase 那邊調整。
